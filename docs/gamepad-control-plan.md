# 手柄控制小车：分阶段实施与审核计划

目标链路：手柄 → RK3576 输入采集 → 控制意图与安全状态 → 带版本/序号的串口协议 → STM32通信状态机 → 10ms速度闭环/舵角映射 → 电机与舵机；MCU速度、编码器、状态和错误计数回传RK，USB独立输出日志。

用户已确认：USB无线接收器手柄；按住使能键才允许运行，松开、掉线或超时即停车。具体手柄型号、轴/键映射尚待识别。

## 当前边界

主界面与UART7/USB诊断通信已经合入，仍不是正式车辆协议。三项审核修复本轮进行编译、主机及硬件验证，结果另列，不能提前视为通过。
电机、舵机、电源使能保持关闭。本轮允许代码框架和无动力验证，不包含接通动力或轮子转动。
每阶段先提交可审查的范围与验收结果，用户确认后进入下一阶段；不得因已有代码/引脚就默认硬件参数已确定。

## 阶段0：消除当前阻塞问题（本轮）

修改：`Core/Src/comm_uart7.c`增加IRQ TX队列及每次服务字节/报文/时间预算；LCD钩子从完成时刻计间隔。
`hardware/AT24C02/`增加有限超时、状态/故障计数、失败后1秒重试间隔；启动读取失败保留默认值。
`Core/Inc/dac_safe.h`统一14处DAC写入换算，非有限值/负数归零，有限越界饱和4095。

验收：Keil编译；真实C模块主机测试覆盖TX阻塞不等待、队列溢出、计时回绕、I2C失败恢复、DAC边界；无动力硬件PING和连续包回归；密集输入时UI仍前进。更新现有PR，保留实测与未验证项。
审核点：确认三项修复及残余风险，然后确定正式协议。

## 阶段1：冻结接口与安全规则（方案待审核）

建议接口：主机输出目标速度mm/s、目标舵角毫度；MCU反馈实测速度mm/s、累计路程mm、原始编码器增量、状态/错误位。
速度PID内部单位须统一，RT1064旧参数以10ms编码器计数为输入，不能直接复制到mm/s。
协议建议新版本，115200 8N1，固定帧头、版本、命令、序号、长度、负载及明确参数的CRC；字节序统一小端。具体字节布局、CRC多项式/初值/覆盖范围和命令号需审核后冻结，当前不暗中选定。
命令范围：HELLO/CAPS、配置与ACK、ARM/DISARM、CONTROL、STATUS、ESTOP；未知命令/长度/CRC错误必须丢弃或明确定义NACK。
配置命令带序号、有限重试并幂等；实时CONTROL只保留最新有效目标，不重复排队重发过期速度。
建议50Hz主机控制发送，200ms控制新鲜度超时（均是待审核初值）；诊断/心跳不得刷新控制新鲜度。
默认按住使能键才允许运动，松开/手柄掉线/串口断线停车；重连不得自动恢复旧速度，需中立位重新使能。急停锁定后需显式复位流程。

框架：`framework/control_gate.[ch]`提供纯逻辑状态门，未链接主固件、不解析UART、不访问GPIO。默认输出关闭；主机测试仅模拟使能后的状态转换。200ms/500mm/s/15度仅为测试数据，不是获准运行参数。
验收：双端协议黄金向量；拆包/粘包、CRC/长度错、重复/过期序号、计时回绕、丢ACK/重试边界测试。
审核点：协议表、状态图、上电/重连/停车策略及参数。

## 阶段2：RK3576手柄输入（先干运行）

上位机建议文件（在smart_car_js独立分支，尚未创建或改动原业务）：
- `control/gamepad_input.*`：Linux evdev/SDL输入适配，具体选择由实际手柄与现有依赖决定；热插拔、设备身份、轴/键映射。
- `control/input_mapper.*`：死区、正反向、速度/转向限制、使能键及急停映射；刚插入设备须完整中立样本后才允许使能。
- `control/command_arbiter.*`：手柄/视觉互斥控制权、优先级、最新目标和新鲜度；视觉模式未审核前禁用。
- `control/control_loop.*`：固定周期发送，退出尽力发DISARM，但停车不能只依赖退出包，MCU超时为最终保障。

前置：手柄型号、USB/接收器/蓝牙方式、Linux事件设备和实际按键轴值。不能从js_branch名称推断已经有手柄驱动。
验收：屏幕/日志显示按键、归一化轴和拟发送目标，禁止打开车辆串口发动力命令；断开手柄100ms级可检测且不保留旧目标；重插不自动ARM。
审核点：实际轴/按钮映射和驾驶方式（摇杆还是扳机）。

## 阶段3：正式双向通信与ACK（不接动力）

STM32建议文件：`Core/Src/car_protocol.c`、`Core/Inc/car_protocol.h`、`Core/Src/car_link.c`；UART驱动只负责有界收发，不直接驱动PWM。
RK建议：`control/protocol_codec.*`、`control/mcu_link.*`；替代旧serial.hpp中不匹配的协议、Kd字段问题及五次重复入队。
使用已审核的control_gate处理会话/使能，绑定模拟输出，日志展示目标与状态，驱动层仍固定关闭。
验收：1000次序号应答、持续流量下界面前进；错误包/丢ACK/重试/断线重连/无CONTROL但有心跳均符合状态机；旧队列不能在重连后驱动车辆。
审核点：双端抓包、状态转换和错误注入报告。

## 阶段4：编码器、电机和舵机校准（必须单独批准动力测试）

建议新增：`encoder_port.[ch]`、`motor_port.[ch]`、`servo_port.[ch]`、`vehicle_calibration.h`。
现有引脚线索：TIM1 PA8/PA9编码器；TIM2_CH2 PA1电机PWM、PA0方向；TIM5_CH3 PA2舵机。须结合实际原理图/接线再次确认。
先不接动力手转轮：核对增量符号、计数倍率、16位回绕、轮径、减速比、每圈计数；10ms读取增量使用有符号回绕差，证明最大可能转速不超过半计数范围。
驱动器型号决定PWM频率与制动/滑行行为，不能沿用当前约50Hz，也不能无依据套用RT1064的5kHz。
舵机先脱开转向连杆，确认中位、最小最大脉宽、方向和机械限位；断线停车时舵机保持/回中/断脉冲须硬件验证后定案。
验收：输出硬限幅、零目标行为、方向切换先归零、轮子悬空低占空比；必要限流与急停有效。
审核点：校准表、示波/逻辑分析/串口记录和供电条件，用户确认后才进入闭环。

## 阶段5：10ms速度闭环与超时停车

建议新增：`speed_controller.[ch]`、`control_scheduler.[ch]`，定时器只安排固定周期工作；不得在ISR里画屏/打印USB/等待I2C。
PID：单位统一、有符号速度、输出限幅、抗积分饱和、停机/重新使能复位、切向与零速处理；第一版限速、限加速度，参数从低增益验证。
超时、死手键、急停、编码器异常均使驱动进入已验证安全状态；目标新鲜度独立于任何遥测/诊断活跃度。
验收：先软件模型和轮悬空，再低速受控地面；阶跃、正反转、编码器断开/回绕、饱和后恢复、丢CONTROL而心跳继续、通讯中断后停车延迟。
审核点：速度曲线、10ms调度抖动、停车响应、PID参数及未覆盖风险。

## 阶段6：手柄整车联调

绑定真实驱动前再次确认使能逻辑，手柄归中→握手/配置完成→用户使能→限速运行。
保留屏幕显示连接状态/目标与实测速度/故障；USB日志作独立证据，日志丢弃不得阻塞控制。
验收：直行、转向、松使能、急停、拔手柄、断串口、RK重启、MCU重启、重新连接均不自动起步；低电压和机械限位处理按硬件能力验证。
视觉作为以后单独模式，未经审核不得与手柄同时写目标。

## 缺失条件清单

手柄型号及轴/按钮映射；完整对应版本原理图；电机驱动器型号、接口极性、允许PWM频率及制动方式；电机/编码器每圈计数、减速比、轮径、方向；舵机型号及实测脉宽和机械限位；动力供电、电源使能与急停接线；最终限速/加速度/转向范围；USB Hub/DAP间歇故障的稳定解决办法。
上述条件不阻止源码框架和主机测试，但会阻止对应硬件阶段验收。本轮不会把未确认参数写成已实现整车能力。
